# 起動・リサイズの性能調査

以下はMVP時点の性能調査です。v1の検索・画像照会を含む測定は[v1検証記録](v1-verification.md#性能)を参照してください。

実施日: 2026-10-25。初回と再実行の差を処理ごとに切り分け、レイアウトの不要な処理を削減した。**再実行は改善したが、ビルド後の初回起動200 ms目標は未達**。

## 環境と測定条件

- Apple M3、物理メモリ16 GiB、macOS 27.0.1（26A434）、arm64。
- Rust 1.92.0、Python 3.9.6。release、`Cargo.lock`固定、`lto="thin"`、`strip=true`。依存の変更なし。
- Python標準ライブラリのPTY、`TERM=xterm-256color`、`--plain`。GUI端末やフォントの描画時間は含まない。
- 起動前に120×40を設定。各runで下移動100回、80×24への幅変更、続けて80×30への高さ変更を測った。各fixtureを5回実行。
- fixtureは直前に生成するため、文書データはページキャッシュに残る条件。OSキャッシュの消去・再起動はしていない。CPU周波数や他アプリの負荷も固定していない。
- 「初回」は新しいビルド成果物の最初の実行。「再実行」は同じ実行ファイルの2〜5回目の中央値。OS再起動直後や新規ダウンロード後を再現した測定ではない。
- 比較対象は`9258b7f`に計測機能だけを加えた版。比較する両版で画面サイズを起動前に固定した。計測中には別のビルド・ベンチマークを並行実行しない。通常段落の修正前測定は単独で取り直した。

全サンプル、fixtureのSHA-256、実行ファイルのSHA-256、追加対照実験は[生データ](performance/2026-10-25.json)に保存した。表は各指標の中央値なので、各処理の中央値の和が合計時間の中央値と一致するとは限らない。

## 測定点

`startup-profile` featureを有効にした開発用ビルドで、次を分けて計時する。

| 指標 | 範囲 |
|---|---|
| `exec_to_main_ms` | PTY子プロセスの`execv`直前からRustの`main`冒頭。両側で`CLOCK_MONOTONIC`を使用 |
| `setup_ms` | 計測初期化、引数解析、TTY判定、シグナル登録 |
| `load_ms` | ファイルを開き、上限・種別を検証し、読込・UTF-8検証・BOM/改行正規化を完了するまで |
| `prepare_ms` | 色指定とファイル名の準備 |
| `parse_ms` | `Document::parse`。数式の区切り走査、Markdown解析、ソース対応を含む |
| `app_ms` | 操作状態とヘルプ文書の作成 |
| `terminal_ms` | raw mode・alternate screen・描画バッファ等の初期化 |
| `layout_ms` | 初回`App::resize`。本文とヘルプの折り返し・ソース対応の構築 |
| `draw_ms` | レイアウト完了後のループ準備と最初の`Terminal::draw`の復帰まで |
| `main_to_flush_ms` | `main`冒頭から最初の本文フレームのflush直後まで |
| `exec_to_flush_ms` | `exec_to_main_ms`と`main_to_flush_ms`の和 |
| `external_startup_ms` | PythonがPTYの準備を始めてから描画末尾をmaster側で受信するまで |

Ratatui 0.29.0の実装で`Terminal::draw`がバックエンドのflush後に復帰することを確認した。計測結果のファイル出力は計時完了後に一度だけ行う。外部計測にはPTY準備・fork・Python側の処理も含まれるため、仕様10.1節に近い起動値には`exec_to_flush_ms`を使う。`execv`呼出前のごく短いPython処理も含む近似で、端末エミュレータの表示完了時刻ではない。

通常ビルドでは計測呼出が空の関数となり、時計読取・計測ファイル出力を行わない。計測用環境変数を通常の起動方法へ追加する必要はない。

## 読込・解析・レイアウト・描画の内訳

従来のベンチマークと同じASCII文書（1,048,576 bytes、10,000行、空行なしの長い一段落）。単位はms。

| 処理 | 修正前・初回 | 修正前・再実行 | 修正後・初回 | 修正後・再実行 |
|---|---:|---:|---:|---:|
| `main`到達前 | 317.09 | 3.03 | 226.29 | 3.69 |
| 読込 | 0.65 | 0.63 | 1.21 | 0.80 |
| 解析 | 4.17 | 3.45 | 4.36 | 4.31 |
| レイアウト | 103.14 | 88.23 | 50.63 | 49.81 |
| 初回描画・flush | 0.51 | 0.39 | 0.41 | 0.40 |
| アプリ内部合計 | 109.09 | 92.76 | 57.36 | 55.79 |
| exec直前〜flush | 426.18 | 96.03 | 283.65 | 59.61 |

修正前の初回と再実行の差は約330 ms。そのうち約314 msが`main`到達前に発生していた。アプリ内部の主な負荷は全体レイアウトで、読込や初回描画ではなかった。

修正後の再実行ではレイアウトが約44%、内部合計が約40%短縮した。一方、初回の合計短縮には`main`到達前の変動も含まれるため、426→284 msの差をすべて最適化の効果とは扱わない。読込・解析自体は変更しておらず、数ms以下の差から性能退行・改善を断定しない。

順序の影響も確認するため、修正前→修正後→修正後→修正前の順で追加計測した（各fixture 3回、移動0回、各組の初回を除く4サンプルの中央値）。ASCIIのレイアウトは85.04→46.44 ms、数式多数は86.95→45.52 msだった。解析はASCIIで3.61→3.73 ms、数式多数で9.96→10.66 ms。主要な短縮がレイアウトで生じる傾向を再確認した。

## 初回の遅延をどこまで切り分けたか

初回の主な追加時間は、ファイル読込やMarkdown処理が始まる前に発生している。今回の分類では**macOS上の実行ファイル読込・ローダー・ランタイム初期化側**に切り分けられる。

さらに修正後の実行ファイルを、内容と署名を変えずに3つの新しいファイルへコピーし、それぞれ3回ずつ起動した。コピー時に新しいinodeを作り、バイナリ内容は同じにした。

| コピー | 1回目の`main`到達前 | 2回目 | 3回目 |
|---|---:|---:|---:|
| 1 | 118.72 | 3.74 | 3.01 |
| 2 | 57.55 | 2.85 | 3.18 |
| 3 | 67.75 | 3.32 | 3.21 |

同じ内容でも新しいファイルの最初の実行で遅延が増えた。この対照実験も、文書処理より前の起動経路に原因があることを支持する。実行ファイルはリンク時のad-hoc署名だった。

ただし、**コード署名検証、dyld、ファイルキャッシュ等のどれが何msかは未特定**。OSの内部トレースや、再起動・キャッシュ消去による実験は行っていない。署名やOSの保護機能を無効にして性能目標を満たす変更は行っていない。

## 実施した改善

- 通常文字の書記素ごとの所有文字列をやめ、結合済み段落文字列から借用する。タブ展開や制御文字の可視化など、変換が必要な場合だけ文字列を確保する。
- `sanitize`は1文字ずつ一時文字列を作らず、一つの出力文字列へ追記する。ESC・NUL・その他の制御文字の表示規則を維持する。
- 書記素から装飾runへの対応は、毎回の二分探索から前進するカーソルへ変更する。装飾境界をまたぐ書記素と元ソース範囲を維持する。
- レイアウト済みの本文幅を保持し、高さだけの変更では本文・ヘルプの全体レイアウトを再実行しない。表示位置の上限調整と再描画は行う。本文幅が変わる場合は従来どおり再レイアウトする。
- PTYの画面サイズを子プロセス起動前に固定し、初期サイズ設定との競合をなくした。これは測定条件の修正であり、アプリ本体の高速化とは区別する。

## 操作・fixture別の結果

再実行の中央値。移動は各runの100イベントに対するnearest-rank p95を算出し、そのrun間中央値を示す。単位はms。

| ASCII文書の操作 | 修正前 | 修正後 | 目標 |
|---|---:|---:|---|
| 下移動100回のp95 | 18.86 | 18.88 | 50 ms以内 |
| 幅変更120×40→80×24 | 110.68 | 62.72 | 200 ms以内 |
| 高さ変更80×24→80×30 | 80.94 | 17.34 | 独立した目標なし |

高さだけのリサイズは約79%短縮した。約17 msには最大60 fpsへまとめる描画ループの待ち時間も含まれる。

計測featureを無効にした通常releaseビルドも、従来の外部計測で確認した。起動は378.39 / 66.02 / 65.16 ms、移動300回のp95は18.84 ms、幅変更は65.13 / 66.01 / 76.66 msだった。外部値にはPTY準備等を含むが、通常ビルドでも再実行は短く、初回だけ大きく増える傾向を確認した。

| fixture（すべて1 MiB） | 内部起動・前→後 | 幅変更・前→後 |
|---|---:|---:|
| ASCII・10,000行、空行なしの一段落 | 92.76→55.79 | 110.68→62.72 |
| ASCII・10,000行、空行を挟む5,000段落 | 56.55→51.69 | 71.42→62.18 |
| 日本語・結合文字・ZWJ絵文字混在、10,000行 | 60.80→46.32 | 75.13→49.30 |
| 表・10,000行（ヘッダと区切り行を含む） | 132.45→99.45 | 148.72→118.67 |
| インライン数式多数・10,000行 | 97.64→61.12 | 111.18→64.80 |
| 改行なし、`word `に続く長い一語 | 62.63→54.38 | 77.23→67.83 |

数式はMVPのTeXテキスト表示で測った。画像生成は含めない。各fixtureはスクリプトで同じバイト列を再生成でき、SHA-256を生データへ保存している。

## 再現手順

処理内訳を測る（このビルド成果物の初回を測る場合は、ビルド後に別途起動しない）。

```sh
cargo build --release --locked --features startup-profile
python3 tests/pty_profile.py target/release/fumi --runs 5 --fixtures ascii paragraphs japanese table math longword
```

同じ内容の新しい実行ファイルで対照実験を行う。各コピーの初回と再実行を分ける。

```sh
python3 tests/pty_profile.py target/release/fumi --runs 3 --moves 0 --copy-binary --fixtures ascii ascii ascii
```

スクリプトは一時ディレクトリのfixture、実行ファイルのコピー、計測JSONを終了時に削除し、結果を標準出力にJSON行として出力する。`--moves 0`で起動・リサイズだけを測れる。手動で計測ビルドを起動する場合は`FUMI_PROFILE`へ計測JSONの新規パスを明示する。既存ファイルは上書きせず、作成できない場合は端末を復旧してエラー終了する。`FUMI_PROFILE_EXEC_NS`はハーネスが`execv`直前に設定するため、通常は手動指定しない。

通常ビルドで外側からだけ測る場合は、従来のベンチマークを使う。

```sh
cargo build --release --locked
python3 tests/pty_bench.py target/release/fumi
```

## 検証と残る課題

- Rust 1.92.0 / 1.99.1でfmt・Clippy（全target・全feature、警告をエラー扱い）・通常テスト18件が成功。表示スナップショット、書記素・ソース対応、制御文字、幅変更時の閲覧位置の既存テストも成功した。
- 高さ変更での閲覧位置保持、本文・ヘルプの上下端調整、最小サイズから同じ幅／異なる幅への復帰を回帰テストへ追加した。
- Rust 1.92.0の通常ビルドと1.99.1の計測feature付きビルドでPTY検証11グループが成功。終了・割り込み・中断再開・初期化失敗・panic時の端末復旧を含む。
- 計測JSONの作成成功、計測先に入力文書と同じ既存ファイルを指定した場合の上書き防止、存在しないディレクトリへの出力失敗時のエラー終了・端末属性復旧もPTYで確認した。
- 初回のexec〜flushは283.65 ms、通常ビルドの外部計測は378.39 msで200 msを超える。再実行59.61 msや内部起動55.79 msだけを使って初回目標達成とは扱わない。配布方法・署名条件を決める際にも、`main`到達前を独立して再測定する必要がある。
- Linuxでの今回の変更、GUI端末の描画遅延、再起動直後や配布先での初回、32 MiB上限の時間・最大メモリは未測定。検索と数式画像生成は後続機能のため未測定。
