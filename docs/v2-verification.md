#### 検証中に見つけた不具合

当初の実装では、数式画像の確認が「生成中」のまま進まなかった。`sample`でプロセスを調べると、端末入力の`read`で止まっていた。macOSの`poll`は`/dev/tty`から開いた端末を待てず、即座にPOLLNVALを返す。このため入力のない`read`へ進んで止まり、キーを押すまでループ（数式の生成・リサイズ・シグナルの確認）が進まなかった。キー操作の確認はキーを送るたびに`read`が戻るため成功しており、気づけなかった。端末入力の待機を`select`へ変えて解消し、待機中のリサイズの確認を加えた。ファイル入力ではfd 0が実際の端末デバイスのため、この問題は起きない。

標準入力のときの数式画像は、PTYの応答エミュレータで確認した。実端末では確認していない。GUI端末での目視とLinuxの実機は未確認。リモートCIは[リモートCIの節](#リモートci2026-11-02)を参照。性能は再測定していない（入力待機の方式を変えたため、性能測定の数値は変更前のバイナリの結果として扱う）。

## macOSのCI失敗とtmux自動設定の待ち時間の分離（2026-11-02）

`80af4d3`をpushした後、GitHub Actionsのmacos-latestで`tests/pty_v1.py`の「tmux 色なしでも画像IDの色を出力」が失敗したとの報告を、エラーログとともに受けた（ubuntu-latestは成功）。

- ログでは、fumiは照会（`a=q`）と仮想配置の試験（`a=T,U=1`）、色の照会を送った後、応答を受け取る前に上限を過ぎて試験画像を削除し、`tmuxで画像対応の確認に応答なし`でTeX表示へ戻っていた。このため画像の配置（`a=p`）を待つ確認が6秒で時間切れになった。
- 原因は、tmuxの自動設定（テストではモックの`tmux`スクリプトの実行）と応答待ちを一つの150 msで数えていたこと。手元のmacOSでは、新しく書いたモックスクリプトの起動は初回約32 ms、2回目以降約3.5 msだった。CIのランナーは起動が遅く、合計が150 msを超えたと判断した。
- `80af4d3`は起動時の画像対応の確認を変更しておらず、`select`へ変えた`77da5d0`ではmacos-latestも成功していた。手元では失敗したテストを75回（CPU負荷下15回を含む）繰り返し、`応答なし`での失敗は再現しなかった。最初の20回のうち1回は理由を記録しないまま別の理由で失敗しており、モックスクリプトの初回起動が遅く自動設定の上限を超えた可能性があるが、確かめていない。

所有者の判断で、自動設定と応答待ちの上限を分けた（[仕様12.11節](../mdview-spec.md#1211-tmux自動設定の待ち時間の分離2026-11-02)）。

### 検証

- `tests/pty_v1.py`に「tmux自動設定が遅くても応答待ちの時間を残す」を加えた。モックの`tmux`に約60 msかかる自動設定を加え、エミュレータは照会を受けてから60 ms遅れて応答する。

- fmt、Clippy（全target・全feature、警告をエラー扱い）成功。Rustテスト64件成功（PTY専用1件はignore）。
- `tests/pty_smoke.py` 12グループ、`tests/pty_v1.py` 25グループ（3回連続、CPU負荷下でさらに2回）、`tests/pty_tmux.py`（実tmux 3.8）6グループ、`tests/pty_v2.py` 10グループが成功した。

## リサイズ中のpanicの修正（2026-11-02）

ユーザーから、fumiを開いた後にウィンドウを小さくすると、次のpanicで終了することがあるとの報告を受けた。

```text
index outside of buffer: the area is Rect { x: 0, y: 0, width: 131, height: 48 } but index is (0, 48)
```

- 端末ループは周回の最初に端末サイズを受け取り、`App::resize`へ渡す。一方、ratatuiの`Terminal::draw`は描画の直前に端末サイズを取り直し、画面のバッファを作り直す。この間にウィンドウが縮むと、`App::draw`は古い高さからステータス行の位置（`height - 1`）を決め、ratatui 0.29の`Paragraph`は範囲外を切り落とさずに添字で書くため、画面の外を指してpanicしていた。ログの例では、受け取った高さが49行、描画時の画面が48行だった。
- MVPから存在した不具合で、v2の変更によるものではない。間の処理（数式の生成管理の更新、画像の転送）が長いほど起きやすい。
- `App::draw`は、受け取ったサイズと描画先の画面の大きさが違えば何も描かずに偽を返す。端末ループはそのフレームを描いていない扱いにし、画像の配置も行わず、次の周回でサイズを合わせ直してから描き直す（[仕様4.1節](../mdview-spec.md#41-レイアウト)）。

### リモートCIでのClippyの警告の修正（2026-11-12）

`6e96aa6`（実装）と`590f4d6`（記録）をmainへプッシュしたところ、GitHub Actionsの[実行43173928865](https://github.com/mentaco/fumi/actions/runs/43173928865)で`test`の両OS（ubuntu-latest・macos-latest）が`cargo clippy`の段階で失敗した。Rust 1.88.0の`msrv`は両OSとも成功した。

- 原因は、CIの`test`が使う安定版Rust 1.99.1のClippyの新しい警告`chunks_exact_to_as_chunks`。定数の大きさの`chunks_exact(4)`が対象で、`src/math.rs`の描いた画素の範囲の判定が該当した。手元のRust 1.92.0のClippyにはこの警告がなく、検出できなかった。同じ書き方が`tests/v2_inline_math.rs`にもあった（ライブラリのエラーで止まり、報告されていなかった）。
- 2か所とも、画素のアルファ値を4バイトおきに読む書き方に改めた（`550bb28`）。警告が勧める`as_chunks`は使わず、最低対応版のRust 1.88でも同じコードが通るようにした。
- 修正後の[実行43176469089](https://github.com/mentaco/fumi/actions/runs/43176469089)で4ジョブすべて成功した。Rust 1.99.1（`test`）と1.88.0（`msrv`）の両OSでRustテスト103件が成功（1件ignore）し、`test`の両OSでPTY検証61グループ（smoke 14、v1 25、tmux 6、v2 16）が成功した。所要時間は`test`がUbuntuで2分8秒、macOSで3分9秒。
- 両OSの`tests/pty_v1.py`で、tmuxの自動設定の確認が1回ずつ再試行された（`RETRY 1/5`。Ubuntuは`tmux自動設定タイムアウト`、macOSは`tmuxで画像対応の確認に応答なし`）。どちらも次の試行で成功した。インライン数式を使わない確認で、tmuxの応答の遅れに備えて元からある再試行。前回の成功時（実行42977265211）は再試行が0回だった。
- 手元のRust 1.92.0とCIの安定版の差で、新しいClippyの警告を手元で検出できない状態は残る。
